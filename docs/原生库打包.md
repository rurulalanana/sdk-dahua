# 大华 NetSDK 平台包（按需打包）

本目录存放**按平台裁剪**的大华原生库，构建时按 profile 打进 `sdk-dahua` 的 jar。

> ⚠️ **整个 `lib/` 不入库**。大华厂商许可禁止随公开仓库分发原生库，
> `sdk-dahua/.gitignore` 已排除。新克隆的仓库需要先按 §1 生成，否则构建会失败。

## 1. 从官方 SDK 生成

官方 SDK 放在 `sdk/dahua/`（同样不入库）。解压后执行：

```powershell
# Windows 原生库
$src = 'sdk\dahua\<Win64 SDK 解压目录>\libs\win64'
Copy-Item "$src\dhnetsdk.dll","$src\dhconfigsdk.dll","$src\libeay32.dll","$src\ssleay32.dll","$src\Infra.dll" lib\win64\

# Linux 原生库
$src = 'sdk\dahua\linux64\<Linux64 SDK 解压目录>\libs\linux64'
Copy-Item "$src\libdhnetsdk.so","$src\libdhconfigsdk.so","$src\libcrypto.so","$src\libssl.so" lib\linux64\
```

## 2. 为什么是这几个库

| 库 | Linux | Windows | 为什么必需 |
|---|---|---|---|
| `dhnetsdk` | 50.45 MB | 32.53 MB | 登录、目录、PTZ、抓图、实时预览、回放 |
| `dhconfigsdk` | 31.12 MB | 8.27 MB | **硬性依赖**：与 `dhnetsdk` 在同一个静态块初始化，缺它整个 `NetSDKLib` 类加载失败 |
| `crypto` / `libeay32` | 2.71 MB | 1.89 MB | TLS 登录 |
| `ssl` / `ssleay32` | 0.48 MB | 0.43 MB | 同上 |
| `Infra` | — | 1.99 MB | Windows 侧 `dhnetsdk.dll` 的依赖 |

合计：Linux **84.8 MB** / Windows **45.1 MB**。

### 刻意剔除

| 库 | 大小 | 原因 |
|---|---|---|
| `avnetsdk` | 29.47 MB | 仅语音对讲；需要时加回并实测 |
| `StreamConvertor` | 27.95 MB | Java API 零引用（已 grep 确认） |
| `play` / `RenderEngine` | 39.76 + 4.46 MB | 依赖 `libX11`/`libGL`/`libEGL`/`libasound`，服务器无图形环境 |
| `ImageAlg` | 0.06 MB | `NetSDKLib` 里那行是注释掉的 |
| `IvsDrawer` | 0.74 MB | 仅智能分析绘图，本平台不用 |

## 3. `dynamic-lib-load.xml` 是白名单，必须与携带的库严格一致

`LibraryLoad.getLoadLibrary()` 遍历清单里当前平台的**全部**库逐个提取，
**整段在同一个 try 里**：任意一个库缺失就抛异常并中断循环，
后面的库（包括 `dhnetsdk`）一个都不会被提取。

更隐蔽的是 `DynamicParseUtil.compareLibName()` 用清单做白名单，
**不在清单里的库名会被解析成空串**，最终拼出 `lib.so`。

因此 `src/main/resources/dynamic-lib-load.xml` 必须与 `lib/<platform>/` 严格对应。
本项目维护的是裁剪版（只列 4~5 个库），**不是**大华原始清单。

> 官方 `netsdk` jar 里也带一份清单，且只列了 `linux64`。
> 在 Windows 上用它会让 `win64` 的库名全部解析为空 ——
> 这是本模块必须**自己提供**清单的原因（classpath 上本模块的 `target/classes` 优先于依赖 jar）。

## 4. 打包方式

`sdk-dahua/pom.xml` 用 profile 按操作系统自动选择平台，
交叉打包用 `-Dnetsdk.platform` 覆盖：

```powershell
mvn -o install -DskipTests                              # 按当前操作系统自动选
mvn -o install -DskipTests "-Dnetsdk.platform=linux64"  # 强制出 Linux 包
mvn -o install -DskipTests "-Dnetsdk.platform=win64"    # 强制出 Windows 包
```

> ⚠️ `-D` 参数**必须加引号**，否则 PowerShell 会在 `.` 处拆开，
> Maven 报 `Unknown lifecycle phase ".platform=linux64"`。
> 这与项目里 `-Dgpg.skip=true` 是同一个坑。

**为什么用 `-D` 而不是 `-P` 切换 profile**：Maven 里「显式 `-P` 激活」与
「`<activation>` 自动激活」的 profile 会**同时生效**，谁最后被求值谁赢，
无法靠声明顺序保证显式指定优先。实测在 Windows 上执行 `-Pnetsdk-linux64`
仍然打出 win64 包。而 `-D` 传入的是「用户属性」，优先级高于 profile 属性，
一定能覆盖。

### 实测产物

| 命令 | jar 大小 | 内含 |
|---|---|---|
| `-Dnetsdk.platform=linux64` | 20.49 MB | `linux64/{libdhnetsdk,libdhconfigsdk,libcrypto,libssl}.so` |
| `-Dnetsdk.platform=win64` | 14.82 MB | `win64/{dhnetsdk,dhconfigsdk,libeay32,ssleay32,Infra}.dll` |

### 切换平台不会残留

`maven-resources-plugin` 只复制、从不删除。若先在 Windows 上打 win64 包、
再打 Linux 包，`target/classes/win64/` 会原样留着，最终 jar 里同时含两个平台：

- jar 体积翻倍（20.5 → 35 MB）
- 更糟的是**两个平台都不会报错**（各自加载自己那份），
  缺陷要很久以后才暴露

本项目其余模块靠 `mvn clean package` 规避，但聚合构建的标准命令是
`mvn -o install -DskipTests`（**不带 clean**），所以不能只靠调用方记得。
`pom.xml` 里用 `maven-clean-plugin` 的额外执行在 `generate-resources` 阶段
清掉所有平台目录，保证 `target/classes` 里只有本次选中的那一个。

> 用 clean 插件而不是 antrun：本机离线构建（`-o`）时 antrun 依赖
> `org.apache.ant:ant`，本地仓库没有，会直接报 `PluginResolutionException`。

### netsdk 的 class 从哪来

原生库在 dahua 的 jar 里，但 **Java class 不在**（`netsdk` 在 dahua 里是
`provided`，不传递）。因此 `gb28181-platform-starter` 显式声明了一份
`compile` 作用域的 `com.netsdk:netsdk`，让 fat jar 自包含、单 jar 可部署。

两份分工：

| 内容 | 来源 |
|---|---|
| `com/netsdk/**` 的 class（4.7 MB） | starter 的 `netsdk` 依赖 |
| `linux64/*.so` 或 `win64/*.dll` | dahua jar（按 profile） |

> `netsdk` 不在中央仓库，构建前必须先 install 到本地仓库（见
> `gb28181-platform-starter/docs/大华SDK接入.md` §8）。
